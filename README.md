# Duosave v2 — локальная база и сайт карточек Duolingo/Drops

Единая локальная база пар «оригинал (pl/es/pt) + перевод (en)» из двух источников:
картинки-карточки Duolingo (`pictures/`) и скриншоты приложений (`screens/`).
Распознавание — бесплатный офлайн-OCR (RapidOCR + PP-OCRv6) с эвристиками раскладки,
нормализацией текста и политикой уверенности; сомнительные кадры попадают в очередь
проверки (страница «Проверка» или экспорт для агентной обработки).

## Куда класть новые файлы

| Папка | Что класть | Как распознаётся |
|---|---|---|
| `pictures/` | **картинки-карточки Duolingo** — то, что сохраняется из приложения кнопкой «Поделиться»/экспортом (квадратная картинка: флаг, фраза и перевод). Это **не** скриншоты. | share-card: язык определяется по флагу, фраза и перевод — из карточки |
| `screens/` | **скриншоты** приложений Duolingo и Drops (обычные снимки экрана телефона, включая парные кадры, перенесённые из `screens_raw/`) | тёмные экраны — Duolingo, однотонные цветные — Drops |
| `screens_raw/` | устаревшая свалка. После слияния здесь остался только мусор без пар (переписки, банки, лидерборды и т.п.) — папку можно очистить или удалить | — |

Новые файлы достаточно положить в `pictures/` или `screens/` и запустить `duosave sync`:
уже обработанное повторно не распознаётся (sha256-кэш + mtime), так что это безопасно в любой момент.

С версии 2.2 картинки можно добавлять и **с любой другой машины**: агент (или вы вручную)
готовит zip-патч в клоне репозитория, а на сайте он загружается на странице
«Обслуживание» (`/admin`) — см. раздел «Патчи: новые картинки с любой машины».
Пути `pictures/`/`screens/` + `duosave sync` остаются для работы прямо на машине с базой.

Для агентов (OpenCode/Codex и т.п.) в репозитории есть `AGENTS.md` с раскладкой, командами
и правилами безопасности данных, и скилл `.agents/skills/duosave-inbox/` для разбора папки
со скриншотами в патч.

## Быстрый старт

```bash
python -m pip install -r requirements.txt        # + rapidocr onnxruntime
python -m duosave init                            # создать БД (data/duosave.db)
python -m duosave sync --folders screens pictures --quiet   # импорт (инкрементальный)
python -m duosave index                           # эмбеддинги (модель ~240 МБ, скачивается один раз)
python -m duosave serve --open                    # http://127.0.0.1:8765
```

`duosave index` при первом запуске скачивает модель эмбеддингов (~240 МБ) в
`data/models/` — дальше всё работает офлайн. Первый гибридный запрос после запуска
сервера медленнее обычного (загрузка модели в память, 2–5 с), последующие — быстрые;
подробности — в разделе «Семантический поиск».

Дымовой прогон: `python -m duosave sync --limit 10`.

## Docker / docker compose

```bash
docker compose up -d --build                                   # сборка и запуск: http://localhost:8765
docker compose exec duosave python -m duosave sync --folders screens pictures --quiet
docker compose exec duosave python -m duosave index
docker compose logs -f duosave                                 # логи
docker compose down                                            # остановить (данные остаются на хосте)
```

База и картинки хранятся **на хосте**, а не в контейнере, поэтому образ можно
пересобирать и удалять без потери данных:

| На хосте | В контейнере | Что там лежит |
|---|---|---|
| `./data` | `/app/data` | `duosave.db` (+ WAL-файлы), кэш распознавания (`cache/`), обрезки Drops (`media/drops/`), миниатюры (`thumbs/`), модель эмбеддингов (`models/`, ~240 МБ), словари (`wordlists/`), а также служебные папки обслуживания: `control/` (запрос и статус исполнителя), `patches/` (отложенные и применённые патчи), `backups/` (снимки БД) |
| `./pictures` | `/app/pictures` | карточки Duolingo |
| `./screens` | `/app/screens` | скриншоты приложений |
| `./screens_raw` | `/app/screens_raw` | входящая свалка (устаревшая) |

- сайт публикуется на `DUOSAVE_PORT` (по умолчанию 8765), страница обслуживания — на
  **отдельном** порту `DUOSAVE_ADMIN_PORT` (по умолчанию 8766): по умолчанию он публикуется
  только на VPN-адрес (`DUOSAVE_ADMIN_BIND_ADDR=10.77.77.21`), чтобы админка не была
  доступна из интернета; `127.0.0.1` оставит её только на самой машине, `0.0.0.0` — на всей
  локальной сети. Если VPN-адаптер ещё не поднят, контейнер не стартует: подключите VPN и
  повторите `docker compose up -d`;
- пути и порт переопределяются в `.env` (образец — `.env.example`), например
  `DUOSAVE_DATA_DIR=/srv/duosave/data`, `DUOSAVE_PORT=9000`;
- новые файлы кладутся в `pictures/`/`screens/` прямо на хосте (папки примонтированы,
  пересборка не нужна), дальше — `docker compose exec duosave python -m duosave sync`;
- первый `duosave index` скачивает модель эмбеддингов в `./data/models/` — интернет
  нужен один раз, дальше всё офлайн;
- на Linux файлы, созданные контейнером (БД, обрезки), принадлежат root: чтобы писать
  в них из-под пользователя, добавьте сервису `user: "1000:1000"`;
- обновление после `git pull`: либо `docker compose up -d --build`, либо кнопкой на
  странице «Обслуживание» — см. «Обновление по кнопке». Коммит вшивается в образ при
  сборке (`DUOSAVE_COMMIT` — build-arg, а не переменная окружения контейнера): по умолчанию
  он берётся из `HEAD` той копии, из которой собирается образ, поэтому в шапке всегда виден
  коммит именно той сборки.

## Команды

| Команда | Что делает |
|---|---|
| `duosave init` | создать БД |
| `duosave sync [--folders …] [--limit N] [--passes 1\|2] [--retry] [--quiet] [--index]` | инкрементальный импорт: sha256-кэш, повторно не распознаёт уже обработанные; `--index` — после импорта обновить эмбеддинги |
| `duosave index [--full]` | эмбеддинги карточек для семантического поиска: инкрементально (только изменённые), `--full` — заново для всех |
| `duosave serve [--host 127.0.0.1] [--port 8765] [--admin-host 127.0.0.1] [--admin-port 8766] [--open]` | локальный сайт: поиск, фильтры, карточки, проверка; второй порт — обслуживание (`--admin-port 0` отключает его) |
| `duosave snapshot [--label manual]` | консистентный снимок БД в `data/backups/` (10 последних на метку) |
| `duosave patch scan\|check\|pack` | машина агента: папка со скриншотами → zip-патч; БД, Docker и данные сайта не нужны |
| `python -m duosave.updater run\|update\|check\|status` | исполнитель обновлений на хосте (задача планировщика; см. «Обновление по кнопке») |
| `duosave stats` | статистика по языкам/источникам/статусам |
| `duosave backfill-time` | дозаполнить время снимка (`created_ts`) для уже импортированных файлов |
| `duosave export [--format csv\|json\|both]` | экспорт CSV по языкам / JSON |
| `duosave agent-queue --out review_queue.jsonl` | очередь кадров, требующих проверки (для агентных батчей) |
| `duosave agent-import results.jsonl` | применить результаты агента/человека к базе |
| `duosave --version` | показать версию |

## Сайт

- поиск без диакритики (`maracuja` → «o maracujá»), фильтры по языку и источнику,
  сортировка по дате снимка (сначала новые / сначала старые);
- дата кадра берётся из имени файла (UNIX-время вида `1680466748.png` или
  `Screenshot_YYYYMMDD-HHMMSS`), иначе — дата создания файла; видна на карточке и в её окне;
- клик по карточке открывает её; фильтры, сортировка и открытая карточка отражаются в URL
  (`/?lang=pt&app=drops&sort=old&card=123`) — такой ссылкой можно поделиться, назад/вперёд работают;
- светлая/тёмная тема (кнопка 🌙/☀️, выбор запоминается);
- «источник: screens/…png» — ссылка на исходный кадр; для Drops показывается обрезанный «образ»;
- в шапке обеих страниц (всегда на виду, не уезжает вниз при подгрузке карточек) —
  две ссылки: `vX.Y.Z` ведёт на репозиторий, короткий хеш коммита — на страницу коммита
  на GitHub; звёздочка у хеша — есть незакоммиченные правки, наведение показывает полный
  хеш и дату. Коммит вшивается в образ при сборке (см. «Обновление по кнопке»): по
  умолчанию это `HEAD` рабочей копии на момент сборки, для сборок без checkout его задают
  через `DUOSAVE_COMMIT` (или `GITHUB_SHA`), URL репозитория — через `DUOSAVE_REPO_URL`;
- иконка вкладки — та же сова, что и в шапке (`duosave/server/static/favicon.svg`; запрос
  `/favicon.ico` перенаправляется на неё);
- третий пункт навигации «Обслуживание» виден **только** когда страница открыта по
  локальному адресу (VPN/LAN, порт обслуживания) — см. «Обслуживание (`/admin`)».

## Обслуживание (`/admin`)

Страница со всеми административными действиями: обновление сайта по кнопке, импорт
патчей с новыми картинками и скачивание бэкапа. Она **не доступна из интернета**: сайт
слушает два порта — публичный (`DUOSAVE_PORT`, по умолчанию 8765, за Cloudflare) и
локальный (`DUOSAVE_ADMIN_PORT`, по умолчанию 8766), и `/admin` вместе с `/api/admin/*`
отвечают только на втором. Из интернета эти адреса отвечают `404`.

- на машине сайта: `http://127.0.0.1:8766/admin`;
- с ноутбука/телефона в VPN: `http://10.77.77.21:8766/admin`;
- локальность определяется портом сокета, на который пришёл запрос, а не заголовками
  `Host`/`X-Forwarded-*` (их можно подделать) — поэтому админку нельзя «попросить» через
  публичный маршрут;
- пункт «Обслуживание» в навигации появляется автоматически, когда страница открыта на
  этом порту.

## Обновление по кнопке

Сайт умеет обновлять сам себя: страница «Обслуживание» пишет файл-запрос в
`data/control/`, а на хосте его забирает исполнитель — `python -m duosave.updater run`,
запущенный задачей планировщика. Контейнер при этом **не получает** ни `docker.sock`,
ни git: всё, что меняет систему, делает хостовый процесс от вашего имени.

Установка (Windows, от имени пользователя, под которым работает Docker Desktop):

```powershell
git pull
powershell -ExecutionPolicy Bypass -File deploy\windows\install-updater.ps1
python -m duosave.updater status        # исполнитель жив?
```

Первая выкатка 2.2 (у контейнера 2.1 кнопки ещё нет): после `git pull` и установки задачи
один раз выполните `python -m duosave.updater update` — он соберёт образ с вшитым коммитом;
дальше можно обновляться кнопкой.

Что делает задание `update`: `git fetch` → проверка ветки (`master`) → `git merge --ff-only`
→ сравнение с коммитом работающего контейнера (совпал — `noop`) → снимок БД
`pre-update-*.db` → сборка образа **из чистого worktree** целевого коммита → `docker compose
up -d --no-build` → проверка здоровья внутри контейнера. Если новый контейнер не поднялся за
120 секунд — откат на `duosave:previous`.

- незакоммиченные правки не мешают: образ собирается из чистого дерева, а `merge --ff-only`
  откажет, только если входящие коммиты конфликтуют с вашими файлами (`failed: not_fast_forward`);
- исполнитель никогда не выполняет `git reset`/`clean`/`stash`/`checkout` в рабочей копии;
- кнопка «Обновить» неактивна, если исполнитель не отвечает, задание уже идёт или обновлять
  нечего; журнал задания — в `data/control/update.log` и на самой странице;
- если во время обновления изменился код исполнителя (`duosave/updater.py`,
  `duosave/control.py`), он завершается с кодом 75, и задача планировщика перезапускает его
  уже с новым кодом;
- удалить задачу: `powershell -ExecutionPolicy Bypass -File deploy\windows\install-updater.ps1 -Remove`
  (файлы в `data/control/` не трогаются).

## Патчи: новые картинки с любой машины

Патч — это zip-архив с картинками и распознанными парами, который готовит агент (или вы)
на любой машине, а сайт применяет в два шага: загрузка → предпросмотр → «Применить».

Машина агента:

```bash
git clone <репозиторий> && cd duosave
python -m pip install -r requirements-agent.txt      # только pydantic + Pillow
python -m duosave patch scan --inbox "D:\Phone\Screenshots"
# агент смотрит картинки и заполняет outbox/.work/slice-NNN.jsonl (скилл duosave-inbox)
python -m duosave patch check                        # 0 — всё готово, 1 — ошибки, 2 — не заполнено
python -m duosave patch pack --agent "opencode · модель"
```

- папка-приёмник **только читается**: ни один файл в ней не меняется; всё рабочее — в
  `outbox/` клона (черновики, журнал `ledger.jsonl`, готовые архивы);
- перед разбором скачайте на `/admin` «Список известных картинок» в `outbox/known-hashes.txt`:
  картинки, которые уже есть в базе, будут пропущены;
- один патч — до 50 МБ на часть (сервер принимает до `DUOSAVE_PATCH_MAX_MB`, по умолчанию 100 МБ);
- загрузка на `/admin`: «Импорт патча» → выбрать zip (по одному) → предпросмотр с миниатюрами
  и итогами (новые/дубликаты/переименованные, новые и существующие карточки) → «Применить»;
  применение идемпотентно, перед ним автоматически делается снимок БД `pre-patch-*.db`;
- после применения карточки `set` сразу видны в поиске, а `review` — на странице «Проверка»;
  семантический индекс обновляется в фоне;
- формат архива и правила заполнения черновиков — `.agents/skills/duosave-inbox/references/patch-format.md`.

## Бэкап и восстановление

На `/admin` есть два варианта скачивания: «Только БД» и «Полный» (БД + картинки). Архивы
отдаются потоком (скачивание начинается сразу) и содержат `backup-manifest.json` с sha256
каждого файла.

- «Только БД»: `data/duosave.db` — консистентный снимок через SQLite backup API;
- «Полный»: плюс `pictures/**`, `screens/**`, `data/media/**`, `data/wordlists/**`; модель
  эмбеддингов, миниатюры, кэш, снимки и служебные папки не входят (модель скачается сама);
- восстановление: `docker compose down` → распаковать архив в корень рабочей копии поверх
  (`Expand-Archive -Force .\duosave-backup-full-….zip .`) → удалить `data/duosave.db-wal`
  и `data/duosave.db-shm`, если остались → `docker compose up -d`. Эмбеддинги лежат в самой
  БД, отдельный `duosave index` не нужен;
- снимки БД лежат в `data/backups/`: `pre-update-*.db`, `pre-patch-*.db` (10 последних на
  группу) и `manual-*.db` (`duosave snapshot`); откатиться можно, просто подменив
  `data/duosave.db` нужным снимком (контейнер при этом остановлен);
- бэкап содержит все ваши данные — храните его как личные данные.

## Безопасность

- сайт (публичный порт) закрыт Cloudflare Access; на входе sitehub включается проверка
  Access-JWT (`cf-access-verify@file`) — см. README sitehub;
- админка живёт на отдельном локальном порту и в интернет не публикуется: по умолчанию
  `DUOSAVE_ADMIN_BIND_ADDR=10.77.77.21` (только VPN). Если порт опубликован на `0.0.0.0`,
  скачать полный бэкап сможет любое устройство локальной сети — проверяйте `curl
  http://<LAN-IP>:8766/api/session` с другого устройства;
- изменяющие admin-запросы требуют собственный заголовок `X-Duosave-Request` и совпадения
  `Origin`/`Host` (CSRF), скачивания запрещены для cross-site запросов;
- у контейнера нет `docker.sock`, git и прав на хост: обновлением занимается хостовый
  исполнитель, а запрос к нему — один файл с перечислимым действием (`update`/`check`);
- при локальном доступе заголовка Cloudflare нет, поэтому в журнале действий
  (`docker logs duosave`) инициатор пишется как `—`.

## Семантический поиск

Поиск по смыслу, а не только по подстрокам: «еда» находит «jedzenie»/«comida»,
«bungee jumping» — «skok na bungee», даже когда буквального совпадения нет.
Всё локально: ONNX-модель через fastembed, без облачных API; тексты карточек и
поисковые запросы не покидают машину.

- в строке поиска три режима: **Текст** (прежний поиск по подстрокам), **Гибрид**
  (текст + смысл, слияние по рангам; по умолчанию) и **Смысл** (только смысловой ранг);
  режим отражается в URL (`?mode=text|semantic`; «Гибрид» — как раньше, без параметра);
  в «Гибриде»/«Смысле» при непустом запросе порядок — по релевантности (сортировка
  по дате действует в «Тексте» и при пустом запросе);
- `duosave index` строит и обновляет индекс: пересчитываются только изменённые карточки,
  `--full` — все; `duosave sync --index` обновляет индекс сразу после импорта;
- модель скачивается один раз (~240 МБ) в `data/models/` при первом `duosave index`,
  дальше всё офлайн; первый гибридный запрос после старта сервера медленнее обычного
  (загрузка модели в память, 2–5 с), последующие — быстрые;
- переиндексировать нужно после `duosave sync` (новые карточки) и правок на странице
  «Проверка»: инкрементальный `duosave index` занимает секунды; пока индекс отстаёт,
  в UI видна подсказка «Семантический индекс отстаёт на N — запустите `duosave index`»;
- без fastembed или без построенного индекса ничего не ломается: поиск работает как
  текстовый (фильтры, сортировка, пагинация — как раньше), в UI — подсказка
  «Семантический поиск недоступен: <причина>»; `duosave index` печатает причину
  и завершается с кодом 2.

### Ручная приёмка

После `duosave index` на реальных данных (режим «Гибрид»):

1. запросы «еда», «bungee jumping», «как сказать "прыжок с тарзанки" по-польски»,
   «travel», «деньги» — в top-10 каждого ожидается **≥ 3 карточки без буквального
   подстрочного совпадения** с запросом (смысловые соответствия на pl/es/pt);
2. латентность: при загруженной модели ответ `api/search` — быстрее 0.5 с (замер во
   вкладке Network в DevTools); первый запрос после старта сервера может быть дольше
   (загрузка модели);
3. деградация: на БД без построенного индекса (`card_embeddings` пуста) поиск в любом
   режиме работает как текстовый, в UI — подсказка с причиной.

## Что хранится

- `cards` — уникальные пары (language, original, translation) со всеми источниками;
- `sources` — ссылки на исходные файлы; для Drops — обрезанная «картинка-образ»
  (`data/media/drops/…jpg`), для Duolingo — путь к исходнику (сайт показывает ссылку на кадр);
- `files` — состояние каждого файла: `auto` / `review` / `skipped` / `reviewed` / `rejected`;
- `patches` — журнал применённых патчей: `patch_id`, sha256 архива, генератор, отчёт,
  кто и когда применил (идемпотентность и аудит);
- `data/control/` — файлы протокола исполнителя обновлений (запрос, статус, журнал, lock);
- `data/patches/` — `staged/` (отложенные, до применения или 7 дней), `applied/` (применённые
  архивы для аудита), `incoming/` (временные файлы загрузки);
- `data/backups/` — снимки БД (`pre-update-*`, `pre-patch-*`, `manual-*`) и временные файлы
  потоковых бэкапов;
- `data/cache/<sha>.json` — кэш распознавания (пересчёт только при изменении логики);
- `data/wordlists/{pl,pt,es}_{50k,full}.txt` — частотные словари (проверка языка и словарный фильтр);
  `golden_set/` — только измерительная обвязка (метрики OCR на золотом наборе), для работы сайта не нужна.

## Политика

Автоматически принимаются только пары, где: оба прохода OCR совпали, язык определён
(для карточек — по флагу), все слова есть в частотном словаре языка, а источник —
карточка или Drops. Экраны приложения Duolingo и всё сомнительное уходит в очередь
проверки (в сайт или в `agent-queue`). Кадры, где OCR не нашёл пары (сборка ответа
из чипов, нестандартные раскладки), тоже попадают в очередь, а не отбрасываются:
их разбирает агент с вижном (`agent-queue` / `agent-import`).
